## 1. Business Context

### 1.1 Purpose

This document defines the business and stakeholder requirements for `patch-ts`, a CLI tool that enables safe, verifiable application of line‑based source code patches generated by AI assistants. It captures the business problem, stakeholders, desired outcomes, business rules, and high‑level stakeholder needs—**without specifying technical implementation details** (which belong in the SRS).

### 1.2 Business Problem / Opportunity

Developers increasingly rely on LLMs to fix compiler errors. The current workflow—copy error, ask LLM, run `sed` command—is brittle:

- Line numbers shift, causing silent corruption.
- Expected content mismatches go undetected.
- Patches can introduce new syntax errors (e.g., unbalanced braces).
- The feedback loop is slow: developer must manually re‑compile, re‑copy errors, and re‑prompt the LLM.

There is no tool that **validates, verifies, and safely applies** LLM‑generated line‑based patches with syntax awareness. `patch-ts` fills this gap, turning a fragile manual process into a safe, iterative collaboration.

### 1.3 Business Scope

**In‑Scope:**

- A CLI tool that applies line‑based patches to Rust source files.
- Content verification before modification.
- Syntax validation after patch (Tree‑sitter AST check).
- Structural repair commands for common issues (unbalanced delimiters).
- Diagnostic output designed for both humans and LLMs.

**Out‑of‑Scope (this initiative):**

- Automatic generation of patches (the LLM generates them).
- Multi‑file or workspace‑wide patches (single‑file only for v1).
- Languages other than Rust (extensible architecture for future).
- IDE plugins or graphical interfaces.

## 3. Business Model & Processes

`patch-ts` is an open‑source developer tool. Its value is delivered directly to individual developers and teams through:

- **Time savings:** avoiding manual debugging of `sed`‑induced corruption.

## 4. Business Rules & Policies

These rules govern how `patch-ts` must behave from a business/stakeholder perspective.

| ID | Rule | Source / Rationale |
|----|------|-------------------|
| **BR‑005** | Never modify a file unless the expected content matches at the target location. | Prevents silent corruption; core safety guarantee. |
| **BR‑006** | Before writing, verify that the patched file parses without new syntax errors (unless overridden). | Protects codebase integrity; aligns with G‑2.1. |
| **BR‑007** | Provide a clear, actionable diagnostic when a patch cannot be applied. | Enables LLM feedback loop; aligns with BR‑003. |
| **BR‑008** | Commands must be expressible in a single shell line (or heredoc) suitable for LLM output. | Ensures LLMs can reliably generate commands. |
| **BR‑009** | Preserve the original file by default (create a `.bak` backup). | Allows recovery from unintended changes. |

## 6. Glossary / Ubiquitous Language

Establishing a shared vocabulary is critical for unambiguous communication with stakeholders and for the LLM to correctly interpret commands.

| Term | Definition | Notes / Synonyms |
|------|------------|------------------|
| **Patch** | A modification to a source code file, typically replacing, inserting, or deleting lines. | |
| **Expected content** | The exact text that must exist at a given line (or range) before a patch is applied. | |
| **Fuzz tolerance** | Allowing the tool to search nearby lines (±N) for the expected content if not found at the exact reported line. | Fuzzy matching, line drift tolerance. |
| **AST validation** | Parsing the patched file with Tree‑sitter to ensure no new syntax errors are introduced. | Syntax check. |
| **Diagnostic** | A structured message explaining why a patch failed, including source snippets and suggestions. | Error report, failure feedback. |
| **Balance** | A repair operation that fixes mismatched delimiters (braces, parentheses, brackets). | Delimiter repair. |
| **Heredoc** | A shell syntax for passing multi‑line strings as input to a command (`<<'EOF' ... EOF`). | Here document. |
| **Dry‑run** | Previewing changes without modifying the file, typically outputting a unified diff. | |

## 7. Conceptual Domain Model

The following high‑level concepts are central to `patch-ts`. They are described in domain terms, not technical implementation.

### Core Entities

- **PatchCommand** – A request to modify a file at a specific location, with expected current content and new content.
- **PatchResult** – The outcome: success (file updated) or failure (diagnostic produced).
- **RepairOperation** – A request to fix structural issues (e.g., `balance`), producing a proposed edit.
- **Diagnostic** – Information about why a patch failed, including context, actual content, and suggestions.

### Relationships

```
PatchCommand ───▶ applied to ───▶ SourceFile
       │                              │
       │ produces                     │ validated by
       ▼                              ▼
PatchResult ◀─── contains ──── Diagnostic
```

### Bounded Contexts

- **Patch Application Context** – Handles line‑based edits, verification, and fuzz matching.
- **Syntax Validation Context** – Uses Tree‑sitter to check AST health.
- **Repair Context** – Analyzes and fixes delimiter mismatches.

*(Note: These are logical groupings; the SRS will decompose into functional requirements.)*

## 9. System‑in‑Context & Operational Concept

### 9.1 System Context

`patch-ts` operates as a command‑line utility invoked by a developer (or script). It interacts with:

- **The file system:** Reads source files, writes patched files, creates backups.
- **The terminal:** Accepts input (heredoc, arguments) and outputs results/diagnostics.
- **The Rust compiler (indirect):** The developer typically runs `patch-ts` between compile cycles; diagnostics are informed by compiler error patterns but not directly integrated.

### 9.2 High‑Level Operational Scenarios

*(These scenarios illustrate the stakeholder experience; detailed behavior will be specified in the SRS.)*

**Scenario A: Successful Single‑Line Replacement**

1. Developer receives compiler error pointing to line 234 in `src/state.rs`.
2. Developer asks LLM for fix; LLM outputs a `patch-ts` command with expected content and new content.
3. Developer runs command. `patch-ts` verifies line 234 matches expected content, replaces it, validates AST, and writes file.
4. Developer recompiles successfully.

**Scenario B: Line Number Drift (Fuzzy Match)**

1. Same as A, but developer had added a comment earlier, shifting the target line to 236.
2. `patch-ts` (with `--fuzz 3`) searches ±3 lines, finds expected content at line 236, and applies patch.
3. Developer recompiles successfully.

**Scenario C: Patch Rejected with Diagnostic**

1. LLM outputs command with expected content that no longer matches the file.
2. `patch-ts` fails, prints diagnostic showing actual line content and diff.
3. Developer copies diagnostic and pastes back to LLM.
4. LLM outputs corrected command with updated expected content.

**Scenario D: Structural Repair After Bad Edit**

1. Developer accidentally introduces an extra `}` during manual editing.
2. Compiler error points to line 566: "unexpected closing delimiter".
3. Developer runs `patch-ts explain --line 566` to understand issue.
4. Developer runs `patch-ts balance --apply`, which removes the extra brace.
5. Developer recompiles successfully.

| ID | Assumption | Impact if False |
